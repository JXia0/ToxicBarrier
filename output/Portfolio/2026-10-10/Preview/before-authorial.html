PROGRESSION THROUGH SPACE
The three regions surround a fixed centre. The first ring keeps early gathering trips close to the tower. Reaching tower Lv.2 opens the second region; Lv.3 opens the third. The upgrade changes both the defence and the space the player can explore.
WHY LEAVE THE REFUGE?
Remaining near the tower is safer, so outward trips need a purpose. Resources fund upgrades and repair supplies help the tower survive. Leaving attack range creates a choice: keep collecting, or return before the journey becomes too dangerous.
FINAL OBJECTIVE  Reach tower Lv.3 and clear every wave and remaining enemy across all three regions.

Code & systems / one upgrade, several connected changes
04 / TOXIC BARRIER
The upgrade is a useful implementation example because it connects resource collection, player proximity, tower combat, visual feedback and access to the next region.
Tower.cs / TryUpgrade()
public bool TryUpgrade(PlayerInventory inventory)
{
    if (!CanUpgrade(inventory))
        return false;

    int targetLevel = NextLevel;
    TowerUpgradeCost cost = GetUpgradeCostForNextLevel();
    if (!TryPayUpgradeCost(inventory, cost))
        return false;

    SetLevel(targetLevel);
    return true;
}
Validation belongs to the tower
The interface requests an upgrade, but Tower.cs decides whether it is valid. CanUpgrade() checks the player’s range, the level cap and the inventory. The same check can update the button state without spending any materials.
TryPayUpgradeCost() checks every resource before consuming any of them. A failed request leaves the inventory unchanged. Only after successful payment does TryUpgrade() call SetLevel().
Proximity, resources and progression are checked before the visible reward.
This separates the upgrade rule from its presentation. The panel can change without rewriting the inventory or level logic.
The visible result
The sprite changes, combat stats update and the upgrade effect plays. The UI refreshes to show the new level and the next cost.
One progression state
OnLevelChanged notifies listeners. Other systems read the tower level instead of maintaining a second, independent upgrade count.
The map reads the outcome
if (mapLevel <= 1) return true;
return tower != null && tower.CurrentLevel >= mapLevel;
MapController.cs keeps region 1 available from the start. Tower levels 2 and 3 unlock the outer rings. One upgrade therefore changes both the strength of the defence and the space the player can explore.
How the project is divided
Core + Player
GameFlowManager.cs handles session flow. PlayerController.cs handles movement. PlayerInventory.cs stores materials.
Map + Loot
MapZone.cs and LevelWavesConfig.cs define regional play. LootManager.cs manages drops, while Tower.cs owns upgrades.
Combat + presentation
HealthSystem.cs handles health and damage. TowerAttackBehavior.cs controls attacks. Camera and rendering scripts present the world.

1 / Notice the warning
The red screen edge signals a nearby parasite. It resembles loot, so gathering is not always safe. The cue gives a reason to slow down and pay attention.
2 / Manage pursuit
The player cannot attack directly. Lead enemies into tower range, or use buildings to change the route and gain space before returning.
3 / Defend the ally
The tower is also vulnerable. The final siege boss can threaten either ally, with a ground warning that allows time to move before impact.
A reason to come back
Repair supplies link exploration to defence. The player carries one parcel back to the tower to restore health. A parcel stays with the player if the tower is already full, rather than being wasted. This creates an intended choice between extending the trip and returning to help the tower.
Keep a destination
The field map uses the actual terrain and shows region states, the tower and discovered supplies. It helps players connect an outward route with the journey home.

Playtest & reflection / making the opening matter
06 / TOXIC BARRIER
Two players / feedback summaries
Player 01: too little pressure
The opening felt too easy. The tower felt too powerful, and the player did not feel under pressure.
Player 02: too straightforward
The game moved straight into play, but the experience felt too direct. This player also described a lack of pressure.
The opening to revisit
What should stay
Keep the player–tower partnership and the three-region unlock structure. Gathering and upgrading should stay central, with stronger decisions about when to explore and return.
My reading of the feedback
Both players reported low pressure. The tower may resolve encounters before the player needs to act. The second response also questions the opening’s purpose and choices. I would test tower strength, encounter pacing and the first objective separately.
Next iteration: proposed changes, awaiting another playtest.
First, test how much the tower does alone
Compare the current version with lower early tower damage or shorter reach. Change one variable at a time and keep the starting resources and encounters comparable.
Watch whether players reposition, lead enemies into range or return to defend. The aim is to make these actions matter while keeping danger understandable and manageable.
